# 파일 단위 자동태깅 개선 계획

> 작성일: 2026-09-02 · 기준 버전 v0.9.8

---

## 1. 결론부터

**파일 단위 자동태깅 기능은 이미 구현돼 있습니다.** 새로 만들 필요가 없습니다.

- `AutoTagDialog.vue`에 **`앨범` / `파일명` 모드 전환**이 이미 있음 (43~65행)
- `POST /api/metadata/auto-tag-by-filename`이 **파일마다** 파일명 파싱 → provider 검색 →
  `find_best_match` → 태그·커버 적용을 SSE 스트리밍으로 수행 (되돌리기 포함)

진짜 문제는 **「멜론 Top100」처럼 트랙마다 앨범이 다른 컴필레이션 폴더에서 이 모드가 제대로 동작하지 않는다**는 것입니다.
이 문서는 새 기능 추가가 아니라 **기존 파일 단위 모드를 컴필레이션에서 쓸 수 있게 고치는** 계획입니다.

## 2. 현재 구조

### 2.1 두 갈래 경로

| 모드 | 진입 | 백엔드 | 동작 |
|---|---|---|---|
| **앨범** (기본값) | 툴바 `🏷 자동태그` → `AutoTagDialog` | `/metadata/album-tracks` + `/metadata/apply-album-cover` | 앨범 하나를 검색해 폴더 전체에 공통 태그 + **폴더 커버 1장** |
| **파일명** | 같은 다이얼로그에서 모드 전환 | `/metadata/auto-tag-by-filename` | **파일마다** 개별 검색·매칭·적용 |
| 파일명 (단건) | 태그편집 패널 `🏷` → `FilenameAutoTagDialog` | **같은 엔드포인트** | 선택한 파일만 |

`FilenameAutoTagDialog`와 `AutoTagDialog`의 파일명 모드는 **같은 엔드포인트**를 씁니다
(`api/metadata.js:18`). 백엔드를 한 번 고치면 두 진입점이 함께 고쳐집니다.

### 2.2 파일명 모드는 이미 갖춰진 게 많다

패턴 프리셋 드롭다운, 패턴 자동 감지(`/browse/detect-filename-pattern`), 변수 삽입 버튼,
현재값 ↔ 파싱값 비교 미리보기, 진행률 스트리밍, `status`별 요약
(`applied` / `kept_existing` / `applied_parsed` / `parse_error` / `error`), 되돌리기(`/metadata/revert-auto-tag`).

## 3. Top100 폴더에서 실제로 깨지는 것

### 3.1 [확인됨 · 치명적] 폴더 커버가 100번 덮어쓰기 된다

`auto_tag_by_filename` 안의 `_apply_cover`:

```python
_write_cover_fn(path_str, img_data, content_type, 3)          # ① 파일에 임베드 — 정상
for old_name in ("cover.jpg", "cover.png", "folder.jpg", "folder.png"):
    if old_f.exists(): old_f.unlink()                          # ② 폴더 커버 삭제
(dir_path / f"cover.{ext}").write_bytes(img_data)              # ③ 폴더 커버 새로 쓰기
```

②③이 **파일마다** 실행됩니다. 트랙 100개가 각기 다른 앨범인 폴더에서는
**100번 지우고 100번 다시 쓰며, 마지막 트랙의 커버가 폴더 커버로 남습니다.** 사실상 무작위입니다.

파일에 임베드되는 ①은 트랙별로 올바릅니다. 문제는 ②③뿐입니다.

**provider 4곳(Spotify·Melon·Bugs·Apple Music) 모두 `cover_url`을 트랙 단위로 반환**하므로,
매칭에 성공한 트랙 수만큼 이 동작이 발생합니다.

> 앨범 모드는 별도 엔드포인트(`/metadata/apply-album-cover`)를 쓰며, 거기서 폴더 커버를 쓰는 건
> **정상 동작**입니다(진짜 앨범 한 장이므로). 이번 수정 대상은 파일명 모드뿐입니다.

### 3.2 [확인됨] 사용자가 파일 단위 모드를 못 찾는다

```js
const mode = ref('album')   // AutoTagDialog.vue:657
```

기본값이 `album`이고, 다이얼로그를 열 때마다 초기화됩니다.
"자동태깅이 폴더 기준 앨범 단위로 되고 있다"는 체감은 여기서 옵니다 — **다른 모드가 있다는 걸 모르는 상태**입니다.

### 3.3 [확인됨] 검색 키가 파일명 하나뿐이다

```python
q_parts = []
if parsed.get("artist"): q_parts.append(normalize_search_query(parsed["artist"]))
q_parts.append(normalize_search_query(parsed["title"]))
query = " ".join(q_parts)
```

검색어는 **오직 파일명 파싱 결과**로만 만들어집니다. 파일에 이미 들어 있는 태그는 쓰이지 않습니다.

게다가 파싱이 실패하면:

```python
if not parsed or not parsed.get("title"):
    status="parse_error" ... continue    # ← 검색을 아예 시도하지 않고 건너뜀
```

멜론에서 받은 파일은 보통 **title/artist 태그가 이미 정확하게** 들어 있습니다.
그 좋은 정보를 놔두고 파일명에만 의존하다가, 패턴이 안 맞으면 그 파일은 통째로 스킵됩니다.

## 4. 개선 설계

### 4.1 커버 정책 분리 (3.1 대응)

파일명 모드에서 폴더 커버를 건드리지 않는 것을 **기본값**으로 합니다.

```
covers 옵션 (요청 본문에 추가)
  "embed"        : 파일에 임베드만 (기본값) ← 컴필레이션 안전
  "embed+folder" : 임베드 + 폴더 커버도 갱신 (기존 동작)
  "none"         : 커버 건드리지 않음
```

**컴필레이션 자동 판별은 하지 않습니다.** "트랙들의 앨범명이 다르면 컴필레이션" 같은 휴리스틱은
태깅 *전*에는 알 수 없고(그래서 태깅하는 것), 틀렸을 때 폴더 커버가 조용히 망가집니다.
기본값을 안전한 쪽으로 두고 체크박스로 사용자가 켜게 하는 편이 낫습니다.

### 4.2 검색 소스 선택 (3.3 대응)

요청에 `search_source`를 추가합니다.

```
"filename"       : 파일명 파싱 (현행, 기본값 유지)
"tags"           : 기존 태그(artist/title)로 검색
"tags_fallback"  : 파일명 우선, 파싱 실패 시 기존 태그로 폴백  ← Top100에 권장
```

구현 부담은 작습니다. `_search_tracks_by_providers(query, ...)`는 이미 **임의 문자열**을 받고,
`find_best_match(parsed, ...)`의 `parsed`도 `{title, artist}` 딕셔너리면 되므로
기존 태그에서 만든 딕셔너리를 그대로 넣을 수 있습니다.

`parse_error` 분기에서 곧장 `continue` 하지 말고, `tags_fallback`이면 태그로 재시도하도록 바꿉니다.

### 4.3 모드 발견성 (3.2 대응)

세 가지 중 택일 — §6 결정 필요:

- (a) **폴더 성격에 따라 기본 모드를 다르게 제안** — 폴더 내 파일들의 `album_title`이 여러 개면
  파일명 모드를 기본 선택. 어디까지나 *기본 선택*이지 자동 실행이 아니므로 3.1의 휴리스틱 문제와는 다름
- (b) **마지막 사용 모드를 기억** (localStorage). 가장 단순하고 예측 가능
- (c) 툴바 버튼을 `🏷 자동태그` 하나에서 `🏷 앨범` / `🏷 파일별` 둘로 분리 — 가장 명시적이지만 툴바가 이미 혼잡

## 6. 결정이 필요한 항목

## 7. 확인이 필요한 것 (측정 안 됨)

- **패턴 하나로 폴더 전체가 커버되는가.** `body.pattern`은 배치 전체에 대해 **문자열 하나**입니다.
  한 폴더 안에 파일명 형식이 섞여 있으면 나머지는 `parse_error`가 됩니다.
  Top100 덤프에서 실제로 얼마나 섞이는지는 아직 재보지 않았습니다.
  §4.2의 태그 폴백이 이 문제도 상당 부분 흡수하지만, 실제 폴더로 확인이 필요합니다.
- **매칭 임계값(기본 70점)이 컴필레이션에서 적절한가.** `score_match`는 제목 60 + 아티스트 30 +
  재생시간 ±20입니다. 트랙별 검색이라 후보 품질이 앨범 모드보다 낮을 수 있습니다.
- **provider rate limit.** 100개 파일 = 최대 100회 검색입니다. `search_cache`가 동일 쿼리는 묶지만
  Top100은 전부 다른 곡이라 캐시 효과가 없습니다. Melon/Bugs 차단 이력(`docs/bugs-403-해결-계획.md`,
  v0.9.7 알송 rate limit 대응)을 고려하면 **배치 딜레이가 필요할 수 있습니다.**

## 9. 구현 결과 (2026-09-02)

§6의 권장안대로 전부 적용했다.

| 항목 | 결정 | 결과 |
|---|---|---|
| `covers` 기본값 | `embed` | 폴더 커버를 건드리지 않음. `embed+folder` 체크박스로 옵트인 |
| `search_source` 기본값 | `tags_fallback` | 파일명 우선, 파싱 실패 시 기존 태그로 폴백 |
| 모드 발견성 | (b) 마지막 모드 기억 | `localStorage: eztag-autotag-mode` |
| 요청 간격 | 신규 `request_delay_ms` (기본 400ms) | 실제 외부 요청이 나갈 때만 대기(캐시 히트는 대기 없음) |

### 실측 검증

**커버 정책** — 임계값 40으로 매칭을 강제하고 3가지 모드를 대조:

| covers | 파일 임베드 커버 | 폴더 cover.jpg |
|---|---|---|
| `embed` (기본) | 있음 | **보존됨** (text/plain 그대로) |
| `embed+folder` | 있음 | 교체됨 (image/jpeg 901KB) |
| `none` | 없음 | 보존됨 |

**검색 소스** — 컴필레이션 흉내 폴더(서로 다른 앨범 4곡, 그중 1곡은 파일명이 패턴에 안 맞음):

| search_source | 결과 |
|---|---|
| `tags_fallback` (기본) | 파싱 성공 3곡 `source=filename`, 실패 1곡은 `source=tags` 폴백으로 **매칭 성공** |
| `filename` (구버전) | 같은 파일이 `parse_error`로 **통째로 스킵** |

**요청 간격** — 검색 4회 기준 `delay=0` 3.65초 → `delay=300ms` 4.61초.

**UI** — 검색 기준 라디오 3개 + 폴더 커버 체크박스 렌더 확인, 기본값(`tags_fallback` 선택 / 폴더 커버 해제) 확인,
모드 기억 동작 확인, 콘솔 에러 0건.

미리보기 표에서 파싱 실패 행이 빨간 `✗ 패턴 불일치`로 표시되면 폴백이 켜진 기본 설정에서는 **거짓 정보**가 되므로,
폴백으로 구제될 행은 주황색 `↩ 기존 태그로 검색`으로 바꿨다.

### 아직 남은 것

- `FilenameAutoTagDialog`(태그편집 패널의 단건 진입)에는 옵션 UI를 넣지 않았다.
  같은 엔드포인트를 쓰므로 **새 기본값은 그대로 적용**되지만, 단건 작업에서 옵션을 노출할 필요는 낮다고 봤다.
- §7의 미측정 항목(패턴 하나로 폴더 전체 커버 가능 여부, 매칭 임계값 적정성, provider rate limit
  실제 한계)은 실제 Top100 폴더로 확인이 필요하다. `request_delay_ms` 기본 400ms는 보수적 추정치다.
